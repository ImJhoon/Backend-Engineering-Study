# [Week 1] 도메인 모델링 (영화관 예약 시스템)

## 🎯 이번 주차 핵심 목표
> 주어진 엔티티들을 바탕으로 개념적 → 논리적 → 물리적 데이터 모델링 과정을 거쳐 최적의 객체지향 설계와 데이터베이스 설계를 도출합니다.
- 영화관 예약 시스템의 핵심 도메인을 파악하고 모델링합니다.
- 엔티티 간의 관계(1:N, N:M 등)를 명확히 정의하고 역할을 분리합니다.

## 📝 필수 도메인 (엔티티) 요구사항
> 아래 8개의 핵심 도메인이 모델링에 반드시 포함되어야 하며, 필요에 따라 속성(필드)이나 추가 엔티티를 자유롭게 정의할 수 있습니다.
- [ ] **User (사용자):** 영화를 예매하는 고객 정보
- [ ] **Movie (영화):** 영화 정보 (예: 제목, 러닝타임, 관람 등급 등)
- [ ] **Theater (상영관):** 영화가 상영되는 물리적인 공간 (예: 1관, 2관 등)
- [ ] **Seat (좌석):** 특정 상영관에 배치된 물리적 좌석 정보 (예: A1, B2 등)
- [ ] **Screening (상영 일정):** 특정 영화가 특정 상영관에서 상영되는 구체적인 일정
- [ ] **Reservation (예약):** 사용자가 특정 상영 일정을 예매한 기본 거래 내역
- [ ] **Reservation_Seat (예약 좌석):** 하나의 예약에 포함된 여러 예매 좌석 정보 (예약과 좌석 간의 다대다 매핑 엔티티)
- [ ] **Payment (결제):** 예약에 대한 실제 결제 내역 (예: 결제 수단, 금액, 상태 등)

## 🛠️ 기술적 제약 및 조건
- **산출물 1:** 개념적/논리적 모델링을 보여줄 수 있는 **ERD (Entity Relationship Diagram)** 문서화.
- **산출물 2:** 물리적 모델링이 반영된 **Spring Data JPA Entity 클래스** 코드로 구현.
- 데이터베이스 테이블 생성 관점을 고려하여 적절한 데이터 타입과 제약 조건(제약 조건, Null 여부 등)을 엔티티에 설정할 것.
- 외래키(FK) 연관관계 매핑(`@ManyToOne`, `@OneToMany` 등)을 적절히 활용할 것.

## 🤔 생각해 볼 포인트
> 이번 과제를 진행하며 함께 고민해보고 목요일 토론 시간에 나눌 주요 안건입니다.
- **연관관계의 방향:** 객체의 연관관계를 단방향으로 끊을 것인가, 양방향 매핑을 허용할 것인가? 양방향 매핑을 썼다면 그 이유는 무엇인가?
- **식별자 전략:** `Reservation_Seat`와 같은 매핑 테이블의 PK(기본키)를 복합키로 가져갈 것인가, 아니면 의미 없는 독립적인 대리키(Auto Increment ID 등)를 사용할 것인가?
- **데이터 생명 주기:** 사용자가 예약을 취소할 경우, 데이터베이스에서 레코드를 완전히 삭제(Hard Delete)해야 할까, 상태값만 변경(Soft Delete)해야 할까?
