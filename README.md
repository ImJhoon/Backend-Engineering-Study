# 📚 Backend Engineering Study

기능 구현이 아니라 **"왜 이렇게 설계했는가"** 를 함께 고민하는 스터디입니다.
매주 동일한 요구사항을 기준으로 각자 예약 시스템을 발전시켜오고, 서로의 설계 의도와 트레이드오프에 대해 토론합니다.

## 🧭 프로젝트 원칙

1. **같은 요구사항, 다른 구현** — 매주 동일한 기능 명세를 각자 자유롭게 설계/구현합니다.
2. **구현은 자유, 기술 스펙 통일** — 언어 버전, 패키지 구조, 네이밍은 자유. 아래 기술 스펙만 통일합니다.
    - 기술 스택: 상단의 `## 🛠️ 기술 스택` 항목 참조
    - 도메인 최소 요소: `Reservation`, `User`, `Resource` 등 (주차별 요구사항에서 안내)
3. **코드 리뷰 필수** — PR로 제출, 최소 1인 이상 리뷰 후 머지. "정답 찾기"가 아니라 "왜 이렇게 했는지" 질문 위주. 설계 관련 리뷰 코멘트는 제출 문서의 "리뷰 받고 수정한 내용"에 반드시 반영합니다.
4. **AI 사용 가능, 단 설명 가능해야 함** — AI 도구 사용은 자유. 다만 발표 시 본인 말로 설명하지 못하면 미완성으로 간주. AI 제안 대안 / 채택·기각 이유를 설계 이유 문서에 구분해서 기록합니다.
5. **설계 이유 문서** — 코드 작성 이후 `docs/weekN.md`(설계 이유 문서)를 작성합니다.

## 📝 주차별 제출 형식 (Week N)

각 주차 제출 문서(`members/{이름}/weekN/README.md`)는 아래 4개 항목을 포함합니다. (템플릿: `templates/week-template.md`)

1. **구현 내용** — 구현한 내용 및 구조도/클래스 다이어그램 등 간단히 (상세 동작 설명 최소화)
2. **설계 이유** — 왜 이 구조/패턴을 선택했는지에 대한 내용, Spring 개념과의 연결
3. **고민했던 부분** — 확신 없었던 지점 혹은 몰랐던 부분, 구현할 때 애매했던 지점
4. **다음 주 개선 계획** — 이번 설계의 한계 중 다음 주제와 연결되는 부분

> 발표 10분 기준, **설계 이유 + 고민했던 부분**에 발표 시간의 절반 이상을 씁니다.

## 🔁 진행 방식

1. 그 주 진행자가 요구사항 확정 → 이슈로 등록 (`week3 요구사항` 등 라벨)
2. 각자 `members/{이름}/weekN` 폴더에서 작업, `week-template.md`를 복사해 설계 이유 문서 먼저 작성
3. 코드 완성 후 브랜치 push, **PR 생성** (제목: `weekN-{이름}: 주제`)
4. 팀원 최소 1인 리뷰 → 리뷰 코멘트 반영 → 문서의 "리뷰 받고 수정한 내용"에 기록
5. 리뷰 완료 후 리뷰한 사람이 Merge
6. 스터디 당일: 개인 발표 10분 + 토론
